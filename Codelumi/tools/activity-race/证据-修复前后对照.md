# 实时活动「重复两张卡」修复 · 证据对照

> 2026-09-25 · 模拟器 iPhone 16 Pro（iOS 27.0）· `SCREEN=activityRace PLAN=yearly`
> 复跑命令：`Allude/tools/activity-race/run.sh`

## 现场（主人截图）

锁屏上并列两张卡，**取件码不同**：`118-5-6178`（上）与 `110-5-6178`（下），
平台与地址相同（菜鸟驿站 / 临沂大学菜鸟驿站）。

「号码不同」是关键信息 —— 说明两张卡是**两次不同时刻**各起的一张活动，
各自冻结在创建时的动态内容上；而不是同一刻并发起的、内容相同的两张。

## 两条根因与对应修法

| 根因 | 现象 | 修法 |
|---|---|---|
| 读-判-写竞态：`activities` 读 + `request` 非原子，两次 sync 重叠时都读到空列表 | 同刻起 2 张（实测 3 张） | `sync` 单飞 + 合并（`@MainActor` 的 `latest` / `converging` + while 消费最新值） |
| 账本同步延迟：新进程读到空列表 → 又 request | 两张卡**内容不同**（截图现场） | 收敛出口 `enforceSingle` 清理 + **延迟 1.2s 复查** |
| `converge` 只 `update(activities.first)` | 重复卡**永不消失**，一直挂到取件清空 | 每次收敛出口都清理；保留策略**优先内容匹配者** |
| 回前台对齐走"内容变了才刷新" | 重复卡不改变数据 ⇒ 永远等不到收敛 | 回前台**无条件**同步一次 + 冷启动对齐一次 |

## 改动文件

- `AlludeShared/PickupActivityController.swift` — 单飞收敛、`enforceSingle`、`settle` 延迟复查、`apply` 拆分
- `Allude/AlludeApp.swift` — 回前台无条件对齐；冷启动对齐（**仅 `activityRace` 跳过**）；`SCREEN=activityRace` 竞态取证；`SCREEN=activityAudit` 只读体检

## 复跑

```bash
Allude/tools/activity-race/run.sh          # 模拟器竞态回归（默认 iPhone 16 Pro）

```

### 真机体检（用户看到的是真机锁屏，模拟器复现只是必要条件）

```bash
Allude/tools/activity-race/device-audit.sh          # 体检 + 取回报告 + 复位为正常模式
Allude/tools/activity-race/device-audit.sh --no-restore
```

实测读数（真机 iPhone 16 Pro，`UDID 00008140-001138A92E01801C`）：

```
audit-0 at-launch    running=1 PASS  isPro=true sysEnabled=true ourToggle=true
    id=4DCAED38-… code=110-5-6178 pending=1 state=active
audit-1 after-align  running=1 PASS
```

**必须把「待办条数」与「活动数」一起读**：`running=0` 有两种相反含义 —— 待办 0 时收起
是正确行为，待办 >0 时才是缺陷。数据在 **App Group 容器**
（`group.com.jikezhang.allude`），与 App 自身容器是两个不同的 domain，取文件时域参数不能混。

### 两个必须知道的取证陷阱

1. **必须注入 `PLAN=yearly`**。实时活动是 VIP 权益，全新安装的模拟器没有凭证 ⇒ `isPro=false`
   ⇒ 第 1 道门 `endAll()` ⇒ 读到 `running=0`，极易误判成「模拟器不支持活动」。
   脚手架里另有一条独立 `probe`，会把 `Activity.request` 的**错误原文**打出来。
2. **ActivityKit 对 request 有频率节流**。同一次启动里反复 `request`/`end` 之后会被拒绝：

   | 读数 | 真实含义 |
   |---|---|
   | `race-D duplicated running=1` | ❌ **不是**"修复了"，而是**两张根本没造出来** |
   | 后续阶段 `running=0` | ❌ **不是**"被收掉了"，而是**没起来** |

   对策：每处 `request` 都打印错误原文；怀疑节流时**重启模拟器**复位（`simctl shutdown` + `boot`），
   不要靠"再跑一遍看看"。实测第一次脚本化复跑撞上了节流，重启后一次通过。
3. `simctl terminate` 有时不生效 —— 若 `launch` 返回的 PID 与上一轮相同，说明 App 从未重启、
   脚手架根本没跑。对比两次 `probe` 的 UUID 即可判定报告是否本轮生成。
